## 📝 1. 영상 전체 요약

> `/handoff` 스킬의 탄생 배경과 설계 원리를 소개하는 영상. 컨텍스트 창의 "Dumb Zone" 문제를 해결하기 위한 기존 `/compact`의 한계를 짚고, 현재 세션의 작업 흐름을 깨지 않으면서 특정 작업을 **별도 에이전트 세션으로 이관**하는 핸드오프 패턴의 실전 활용법을 그릴링·프로토타이핑 세션 예시와 함께 설명한다.

## 📖 2. 영상 주요 주제 (추상화된 목차)

*   **도입 — 핸드오프 스킬의 탄생 배경**

    - **세부 주제:** 컨텍스트 창의 Smart Zone vs Dumb Zone — 약 120k 토큰 이후 에이전트의 주의(attention) 관계가 희박해져 응답 품질이 저하되는 현상
    - **세부 주제:** `/compact`의 역할과 한계 — 단일 세션을 장기 운영할 때 유용하지만, 다른 세션으로 분기하거나 현재 진행 내용을 보존하면서 새 세션을 시작할 수 없음

*   **핵심 기능 — /handoff 스킬의 설계와 동작 원리**

    - **세부 주제:** 스킬의 핵심 동작 — 현재 세션의 컨텍스트를 압축하여 마크다운 핸드오프 문서로 저장, OS 임시 디렉토리에 보관
    - **세부 주제:** 핸드오프 문서의 구성 요소 — 다음 세션의 포커스, 추천 스킬 섹션, 민감 정보 제외, 기존 아티팩트 중복 제거(포인터 사용), 사용자 전달 인수(목적) 반영
    - **세부 주제:** 핸드오프 호출 시 목적(reason)을 명시하는 것이 핵심 — 다음 세션이 무엇에 집중할지 알아야 좋은 문서 작성 가능

*   **심화 활용 — 그릴링·프로토타이핑 세션과의 연계 패턴**

    - **세부 주제:** 그릴링 중 스코프 외 작업 분리 — 현재 세션의 집중도를 유지하면서 별도 이슈나 버그 픽스를 다른 에이전트에게 이관
    - **세부 주제:** 그릴링 → 프로토타입 → 그릴링 복귀 패턴 — "알 수 없는 것"을 프로토타입으로 확인하고 학습 결과를 핸드백(hand-back)하는 DIY 서브에이전트 구조
    - **세부 주제:** 크로스 에이전트 호환성 — 마크다운 파일 기반이므로 Claude Code → Codex / Copilot CLI 등 다른 에이전트로도 자유롭게 이관 가능, 적대적 리뷰(adversarial review)에도 활용

*   **결론 — 핸드오프를 실전에서 극대화하는 방법**

    - **세부 주제:** 핸드오프 호출 시 항상 목적과 이유를 명시하는 습관 — 음성 딕테이션으로 빠르게 전달
    - **세부 주제:** 핸드오프 파일은 임시 파일 — 장기 문서가 아닌 일회성 이관 도구로 다룰 것

*(참고: 이 항목은 영상의 논리적 구조를 추상화하여 그룹화한 것이며, 시간 정보는 포함되지 않습니다.)*

## ⏳ 3. 주요 시간대별 상세 요약

*   **[00:00:00] ~ 도입 — 핸드오프 스킬이 탄생한 이유**

    - 에이전트를 사용하다가 "이 정도로 단순한 건 스킬이 필요 없겠지" 라고 생각했던 핸드오프 패턴을 결국 스킬로 만들게 된 계기 설명
    - 핸드오프 스킬의 핵심 동작: 현재 세션의 컨텍스트 창을 압축해 마크다운 파일로 저장 → 다른 세션에 전달
    - 스킬 저장 위치: `skills/productivity/handoff` (깃허브 스킬 레포, 100K 스타 근접)



*   **[00:02:00] ~ Smart Zone vs Dumb Zone — 컨텍스트 창의 현실**

    - Claude Code의 컨텍스트 창은 100만 토큰이지만, 실질적으로 사용 가능한 **Smart Zone은 약 120k 토큰**
    - 토큰이 쌓일수록 어텐션 관계(attention relationships)가 희박해져 에이전트 응답 품질 저하
    - 120k 토큰 이후 = Dumb Zone: 에이전트가 멍청한(dumber) 결정을 내리기 시작
    - 항상 컨텍스트 창 사용량을 모니터링하고 효율적으로 예산을 관리해야 함



*   **[00:04:00] ~ /compact의 역할과 한계**

    - `/compact`는 긴 대화를 요약하여 컨텍스트를 Smart Zone으로 되돌리는 표준 방법
    - Auto-compact 버퍼: 컨텍스트가 Dumb Zone 깊숙이 차면 자동으로 요약 실행 (하네스 설정에 따라 다름)
    - **compact의 한계**: ① 현재 세션의 진행 내용을 덮어씀 → 현재 작업을 보존하면서 새 세션 시작 불가, ② 여러 번 compact하면 이전 대화가 "퇴적층"처럼 쌓여 비효율 발생
    - compact의 적합한 용도: 단일 문제를 오래 파고드는 디버깅 세션 (이미 시도한 것들을 compact로 저장하며 계속 시도)



*   **[00:06:30] ~ /handoff 스킬 탄생 — compact의 대안**

    - 탄생 계기: 그릴링 중 스코프 밖 리팩토링 기회를 발견했을 때, 현재 세션을 희석시키지 않고 분리된 세션에 이관하고 싶었음
    - 기존 방법: 수동으로 "핸드오프 문서 작성해줘" 라고 요청 → 너무 자주 반복되어 스킬화 결정
    - 스킬의 핵심: **현재 세션은 그대로 유지**하면서, 특정 작업만 별도 마크다운 파일로 분리해 다른 에이전트에게 전달



*   **[00:08:00] ~ 실전 예시 1 — 그릴링 중 스코프 분리**

    - Sandcastle(소프트웨어 팩토리) 피처 플래닝 그릴링 세션 예시
    - Q2 중에 "반복(iterations)과 완료 신호를 별도 API로 분리하자"는 아이디어 발견
    - 핸드오프 호출 시 이유(reason)를 명시: "이 작업을 별도 에이전트에게 이관한다"
    - 두 가지 효과: ① 현재 그릴링 세션의 스코프가 명확히 좁혀짐(Q2 collapse), ② 분리된 작업이 별도 핸드오프 파일로 생성되어 나중에 GitHub 이슈로 처리



*   **[00:10:00] ~ 실전 예시 2 — 그릴링 → 프로토타입 → 그릴링 복귀 패턴**

    - Q13까지 진행된 그릴링 세션에서 "window communication, TL;Draw SDK 통합"이라는 고피델리티 질문 발생
    - 핸드오프로 프로토타이핑 세션 생성 → 해당 세션에서 169K 토큰을 사용해 UI 프로토타입 구현
    - 프로토타입 세션 완료 후 역방향 핸드오프: "프로토타입에서 얻은 학습 결과를 원래 그릴링 세션으로 전달"
    - **DIY 서브에이전트 구조**: 부모 세션 → 자식 세션(프로토타이핑) → 부모 세션 복귀
    - 최종적으로 그릴링 완성 → PRD 및 GitHub 이슈 생성



*   **[00:13:00] ~ 스킬 설계 원칙 상세 설명**

    - **추천 스킬 섹션 포함**: 다음 세션에서 호출해야 할 스킬(grill with docs, diagnose, prototype 등)을 문서에 명시 → 다음 세션 시작 즉시 올바른 스킬 호출 가능
    - **중복 제거 원칙**: 이미 다른 마크다운 파일·GitHub 이슈에 있는 내용은 반복하지 않고 포인터로 대체 → 문서 비대화 방지
    - **임시 디렉토리 저장**: 핸드오프 파일은 OS 임시 폴더에 저장, 코드베이스 문서로 오래 남기지 않음
    - **민감 정보 제거**: API 키·패스워드·PII 자동 제외
    - **목적(args) 반영**: 사용자가 전달한 목적을 기반으로 다음 세션에 최적화된 내용으로 문서 구성
    - **크로스 에이전트 호환**: 마크다운 파일이므로 Claude Code → Codex, Copilot CLI 등 어떤 에이전트에도 전달 가능 → 다른 에이전트 간 적대적 리뷰(adversarial review)에도 활용 가능



*   **[00:16:00] ~ 마무리 — 핸드오프 사용의 핵심 습관**

    - 핸드오프 호출 시 **항상 목적과 이유를 명시** — 이것 없이는 좋은 핸드오프 문서를 작성할 수 없음
    - 음성 딕테이션으로 이유를 빠르게 전달하는 것이 실전 팁
    - 몇 주 만에 만든 스킬이지만 일상에서 가장 자주 사용하는 스킬 중 하나가 됨
