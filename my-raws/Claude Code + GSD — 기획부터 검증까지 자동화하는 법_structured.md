## 📝 1. 영상 전체 요약

> Claude Code 위에 설치하는 메타프롬프팅 시스템 GSD(Get Shit Done)가 컨텍스트 롯(Context Rot) 문제를 서브 에이전트 격리·구조화된 문서 전달·원자적 계획 실행으로 해결하는 원리를 분석하고, GSD를 사용하지 않더라도 즉시 적용 가능한 컨텍스트 엔지니어링의 3가지 핵심 원칙(문서화·작업 분해·검증 자동화)을 제시한다.

---

## 📖 2. 영상 주요 주제 (추상화된 목차)

*   **[문제 진단: 컨텍스트 롯(Context Rot)이란]**

    - **세부 주제:** Claude Code의 구조적 한계 — 컨텍스트 윈도우(메모장)가 가득 찰수록 품질 저하. 앞서 정한 규칙 망각, 같은 실수 반복, 코드 스타일 중구난방, 심하면 자기가 짠 코드를 덮어씀
    - **세부 주제:** 악순환 구조: 처음엔 잘 되니까 계속 시킴 → 프로젝트가 커지면 컨텍스트 폭발 → 버그 쏟아짐 → 고치려고 또 시키면 더 꼬임 → "AI 코딩은 프로토타입까지만"이라는 인식 고착

*   **[GSD 개요: 메타프롬프팅 시스템]**

    - **세부 주제:** GSD = Claude Code 위에 설치하는 메타프롬프팅 시스템. 코드를 대신 짜는 도구가 아니라 Claude Code가 잘 짜게 만드는 도구. 설치: `npx gtd` 한 줄 → Claude Code 내 슬래시 커맨드 추가
    - **세부 주제:** 개발자 철학: "나는 솔로 개발자, 코드를 안 짠다, Claude Code가 짠다." 스프린트·스토리·레트로스펙티브 등 엔터프라이즈 프로세스 불필요. Amazon·Google·Shopify 엔지니어 사용 중

*   **[GSD 5단계 워크플로우]**

    - **세부 주제:** ① `/gsd new-project`: 질문 쏟아내기 — 무엇을 만들지, 기술 스택, 제약 조건, 엣지 케이스. 답변에서 자동으로 project.md·requirements.md·roadmap.md 생성. 머릿속의 애매한 기획을 구체화
    - **세부 주제:** ② `/gsd discuss [페이지]`: 해당 단계의 모호한 부분 발굴 — 레이아웃(카드 vs. 테이블), 에러 처리(토스트 vs. 인라인) 등. 이 단계를 건너뛰면 Claude Code가 임의로 결정 → 나중에 수정 비용 발생
    - **세부 주제:** ③ `/gsd plan [페이지]`: 라이브러리·패턴 리서치 → XML 형식 계획서 생성(태스크명·수정 파일·구체적 행동·검증 방법) → 자체 검증(목표 달성 여부 확인, 불합격 시 재작성). 통과까지 반복
    - **세부 주제:** ④ `/gsd execute [페이지]`: 계획서를 웨이브 단위로 묶어 실행 — 의존성 없는 계획서는 같은 웨이브에서 병렬 실행, 의존성 있는 것은 다음 웨이브에서 순차 실행. 각 계획서마다 새 서브 에이전트(프레시 컨텍스트 20만 토큰) 생성. 태스크 완료마다 자동 git 커밋
    - **세부 주제:** ⑤ `/gsd verify [워크]`: 자동 검증 — 코드 존재 여부·테스트 통과 확인 후 사용자에게 직접 확인 요청("로그인 되나? 버튼 동작하나?"). 문제 발견 시 디버그 에이전트 생성 → 원인 분석 → 수정 계획서 → 재실행

*   **[컨텍스트 롯 원천 차단 3가지 메커니즘]**

    - **세부 주제:** ① 서브 에이전트 격리: 오케스트레이터(팀장)는 교통 정리만 → 컨텍스트 30~40%만 차지. 서브 에이전트(팀원)는 각자 plan.md만 읽고 독립 컨텍스트에서 담당 부분만 처리 → 아무도 컨텍스트가 가득 차지 않는 구조
    - **세부 주제:** ② 구조화된 문서 전달: 채팅 히스토리 대신 구조화된 마크다운 파일만 전달(project.md·requirements.md·state.md). "잡다한 10만 토큰보다 핵심만 정리된 2만 토큰이 훨씬 낫다" — 컨텍스트의 양이 아닌 질
    - **세부 주제:** ③ 원자적 계획 실행: 하나의 계획서 = 하나의 서브 에이전트 컨텍스트 안에서 완결 가능한 크기로 분해. 각 계획서에 검증 단계 포함(특정 커맨드 결과값·테스트 통과 조건) → 실행 에이전트가 스스로 검증

*   **[컨텍스트 엔지니어링: 프롬프트 엔지니어링의 다음 단계]**

    - **세부 주제:** GSD가 해결하는 진짜 문제 = AI↔인간 커뮤니케이션 문제. "대충 이런 느낌으로 만들어 줘 → 대충 이런 느낌으로 나옴" 패턴 해결
    - **세부 주제:** 컨텍스트 엔지니어링 정의: AI에게 올바른 컨텍스트를 올바른 타이밍에 올바른 형태로 전달하는 기술. 프롬프트 엔지니어링(어떻게 말하냐)의 다음 단계. 컨텍스트 엔지니어링(무엇을 언제 얼마나 보여주냐)
    - **세부 주제:** GSD의 모든 설계가 컨텍스트 엔지니어링 관점에서 설명됨 — 질문 많이 하는 이유(올바른 컨텍스트 추출), 문서 만드는 이유(컨텍스트 구조화), 서브 에이전트 쓰는 이유(필요한 컨텍스트만 전달)

*   **[GSD 없이도 적용 가능한 3가지 원칙]**

    - **세부 주제:** ① 대화 줄이고 문서 늘리기: Claude Code에 채팅으로 지시하는 대신 CLAUDE.md에 프로젝트 구조 정리, 스킬 파일에 반복 지시 문서화 → 컨텍스트의 질 향상
    - **세부 주제:** ② 큰 작업은 원자적으로 분해: "이 앱 전체 만들어 줘"(최악) → "로그인 API부터 만들어 줘, 스펙은 이거야, 끝나면 이 테스트로 확인해 줘" → 컨텍스트 오버플로우 방지
    - **세부 주제:** ③ 검증 자동화: 테스트 코드를 먼저 작성 후 구현 위임 → 테스트 통과 여부로 완료 판단. 안전망이 있으면 마음 놓고 위임 가능

*(참고: 이 항목은 영상의 논리적 구조를 추상화하여 그룹화한 것이며, 시간 정보는 포함되지 않습니다.)*

## ⏳ 3. 주요 시간대별 상세 요약

*   **[00:00:00] ~ 도입: 컨텍스트 롯 문제**

    - Claude Code 사용 패턴: 처음엔 천재(파일 구조 파악, 코드 작성, 테스트 자동화) → 1시간 후 갑자기 아까 만든 파일 망각, 방금 정한 규칙 무시, 자기 코드 덮어쓰기
    - 컨텍스트 롯(Context Rot) 정의: 컨텍스트 윈도우가 차면서 품질이 썩는 현상. 작업할수록 Claude Code가 멍청해짐
    - 악순환: 처음엔 잘 되니까 계속 시킴 → 프로젝트 커지면 버그 쏟아짐 → 더 꼬임 → "AI 코딩은 프로토타입까지만" 인식 고착

*   **[00:02:00] ~ GSD 소개: 메타프롬프팅 시스템**

    - GSD(Get Shit Done / "개치던이"): Claude Code 위에 설치하는 메타프롬프팅 시스템. 설치: `npx gtd` 한 줄 → Claude Code 내 슬래시 커맨드 추가
    - 핵심 구분: 코드를 대신 짜는 도구(×) / Claude Code가 잘 짜게 만드는 도구(○) = 컨텍스트 관리 시스템
    - 개발자 철학: 솔로 개발자, 코드 안 짬, Claude Code가 짬. Amazon·Google·Shopify 엔지니어 사용 중

*   **[00:03:30] ~ GSD 5단계 워크플로우**

    - 1단계 `/gsd new-project`: 질문 쏟아내기(무엇을, 기술 스택, 제약, 엣지 케이스) → project.md·requirements.md·roadmap.md 자동 생성
    - 2단계 `/gsd discuss [페이지]`: 모호한 부분 발굴(레이아웃·에러 처리 방식 등). "이 단계를 건너뛰면 Claude Code가 임의 결정 → 나중에 수정 비용"
    - 3단계 `/gsd plan [페이지]`: 라이브러리 리서치 → XML 형식 계획서(태스크명·수정 파일·행동·검증 방법) → 자체 검증(통과할 때까지 재작성)
    - 4단계 `/gsd execute [페이지]`: 의존성 기반 웨이브 분류 → 각 계획서마다 새 서브 에이전트(프레시 20만 토큰 컨텍스트) → 태스크 완료마다 자동 git 커밋
    - 5단계 `/gsd verify [워크]`: 자동 검증(코드·테스트) → 사용자에게 직접 확인 요청 → 문제 시 디버그 에이전트 생성 → 수정 계획서 → 재실행

*   **[00:07:00] ~ 컨텍스트 롯 원천 차단: 3가지 메커니즘 상세**

    - 메커니즘 1 — 서브 에이전트 격리: 오케스트레이터(팀장) = 교통 정리만, 컨텍스트 30~40% 유지. 서브 에이전트(팀원) = plan.md만 읽고 독립 컨텍스트에서 담당 부분 처리. 아무도 컨텍스트가 가득 차지 않음
    - 메커니즘 2 — 구조화된 문서 전달: 채팅 히스토리 없이 구조화된 마크다운만 전달. "잡다한 10만 토큰보다 핵심 2만 토큰이 낫다" — 컨텍스트의 질이 결과의 질을 결정
    - 메커니즘 3 — 원자적 계획 실행: 서브 에이전트 컨텍스트 안에서 완결 가능한 크기로 계획서 분해. 각 계획서에 검증 조건 포함 → 에이전트 스스로 완료 판단. 팀원에게 "다 하면 이거 확인해봐"까지 적어주는 구조

*   **[00:10:30] ~ 컨텍스트 엔지니어링: 더 큰 관점**

    - GSD가 진짜 해결하는 문제: AI↔인간 커뮤니케이션. "대충 이런 느낌으로 만들어 줘"의 대충이 문제
    - 컨텍스트 엔지니어링: AI에게 올바른 컨텍스트를 올바른 타이밍에 올바른 형태로 전달. 프롬프트 엔지니어링(어떻게 말하냐) → 컨텍스트 엔지니어링(무엇을 언제 얼마나 보여주냐)
    - GSD 설계 의도 통합 설명: 질문(올바른 컨텍스트 추출) + 문서(컨텍스트 구조화) + 서브 에이전트(필요한 컨텍스트만 전달)

*   **[00:12:30] ~ GSD 없이 적용하는 3가지 원칙**

    - ① 대화 줄이고 문서 늘리기: CLAUDE.md에 프로젝트 구조, 스킬 파일에 반복 지시 문서화
    - ② 원자적 작업 분해: "이 앱 전체"(최악) → "로그인 API 먼저, 스펙 이거야, 테스트로 확인해줘"
    - ③ 검증 자동화: 테스트 코드 먼저 → 구현 위임 → 테스트 통과로 완료 판단
    - 결론: 컨텍스트 윈도우가 아무리 커져도 쓰레기를 많이 넣으면 쓰레기 나옴. "무엇을 넣느냐가 항상 핵심" — 컨텍스트 엔지니어링은 AI 도구 성능 향상과 무관하게 사라지지 않을 핵심 역량
