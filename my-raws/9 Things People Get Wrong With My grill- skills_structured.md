## 📝 1. 영상 전체 요약

> Grill Me / Grill with Docs 스킬을 사용할 때 흔히 저지르는 9가지 실수를 분석하고 올바른 사용법을 설명한다. 핵심 메시지는 "이 스킬은 엔지니어를 대체하는 것이 아니라 보조하는 도구"이며, 질문의 피델리티(fidelity) 이해·적절한 스코프 설정·능동적 참여·컨텍스트 보존·스마트 모델 선택·병렬 세션이라는 6가지 렌즈를 통해 실패 원인을 명확히 진단한다.

## 📖 2. 영상 주요 주제 (추상화된 목차)

*   **도입 — Grill Me 스킬의 본질과 실패의 원인**

    - **세부 주제:** Grill Me 스킬은 LLM이 아닌 **사용자의 기획력**에 의존하는 도구 — 스킬 자체보다 스킬을 다루는 사람의 역량이 결과를 결정함
    - **세부 주제:** 실패를 이해하기 위한 3가지 렌즈 — 질문의 피델리티(고/저), 스코프의 크기, 능동/수동 참여 정도

*   **핵심 개념 1 — 질문의 피델리티와 Grillable/Ungrillable 구분**

    - **세부 주제:** 고피델리티 질문(Ungrillable) — "이 UI가 실제로 어떤 느낌인가"처럼 실제로 만들거나 프로토타입을 봐야만 답할 수 있는 질문
    - **세부 주제:** 저피델리티 질문(Grillable) — "이 라우트의 URL을 무엇으로 할까"처럼 대화만으로 답할 수 있는 질문
    - **세부 주제:** Ungrillable 질문 발견 시 처리법 — 핸드오프 스킬로 프로토타이핑 세션으로 전환 → 확인 후 원래 그릴링 세션으로 복귀

*   **핵심 개념 2 — 스코프 관리와 컨텍스트 경제학**

    - **세부 주제:** 스코프가 너무 크면 발생하는 두 가지 문제 — ① 숨겨진 고피델리티 질문 발생, ② 컨텍스트 창의 "Dumb Zone"(~120k 토큰) 도달
    - **세부 주제:** 올바른 접근법 — 큰 스코프를 미리 작은 스코프들로 분해하고, 각각을 개별 그릴링 세션에서 처리
    - **세부 주제:** 그릴링 세션에서 쌓인 컨텍스트(설계 결정, Q&A)는 매우 귀중한 자산 — 절대 버리지 말고 PRD나 핸드오프 문서로 보존

*   **핵심 개념 3 — 능동적 참여와 모델 선택**

    - **세부 주제:** 너무 수동적인 참여 — LLM이 수백 개의 질문을 쏟아내거나 스코프를 폭발시키도록 방치하는 실수
    - **세부 주제:** 너무 능동적인 참여 — 저피델리티 질문에 지나치게 오래 머물며 코드 구현으로 넘어가지 못하는 실수
    - **세부 주제:** 그릴링에는 반드시 **스마트 모델** 사용 — 그릴링은 모델의 파라메트릭 지식(훈련된 이해)에 의존하므로 대형 프론티어 모델이 필수. 구현 단계에서는 컨텍스트 지식이 주를 이루므로 더 작은 모델도 가능

*   **결론 — 병렬 그릴링과 핵심 요약**

    - **세부 주제:** 두 개 세션을 동시에 그릴링하는 병렬 전략 — 한 세션이 응답을 생성하는 동안 다른 세션에 답변하며 처리량 2배 달성
    - **세부 주제:** 9가지 실수 종합 요약 및 그릴링 숙련도는 연습을 통해 향상 가능하다는 메시지

*(참고: 이 항목은 영상의 논리적 구조를 추상화하여 그룹화한 것이며, 시간 정보는 포함되지 않습니다.)*

## ⏳ 3. 주요 시간대별 상세 요약

*   **[00:00:00] ~ 도입 — 스킬의 본질과 영상 목적**

    - Grill Me / Grill with Docs 스킬 사용 중 "LLM이 200개 질문을 했다"는 피드백을 자주 접함 → 스킬 자체보다 사용자의 기획 역량이 핵심임을 강조
    - 이 스킬은 엔지니어를 대체하는 것이 아니라 보조하는 도구 — 스코프 이해, 피델리티 판단, 질문에 답하는 능력은 사람이 담당해야 함
    - 9가지 실수를 다루기 전에 실패 모드를 이해하는 렌즈 3가지 먼저 소개



*   **[00:02:00] ~ 렌즈 1 — 질문의 피델리티 (Grillable vs Ungrillable)**

    - Ryan Singer의 "Shape Up"에서 차용한 개념: 고피델리티 질문 vs 저피델리티 질문
    - **고피델리티(Ungrillable)**: "이 폼 필드를 여러 페이지로 나눌까, 하나의 긴 폼으로 할까?" → 프로토타입이나 실제 구현을 봐야 답 가능
    - **저피델리티(Grillable)**: "이 라우트의 URL은?" → 대화만으로 즉시 답 가능
    - **Ungrillable 질문 처리법**: 핸드오프 스킬 → 프로토타이핑 세션 → 결과를 원래 그릴링 세션에 핸드백(handback)
    - 실패 모드 ①: 그릴링 세션 중 고피델리티 질문을 억지로 답하려는 것



*   **[00:05:00] ~ 렌즈 2 — 스코프 크기와 컨텍스트 관리**

    - 스코프가 너무 크면 두 가지 문제: ① 아직 검증되지 않은 기반 위에 계속 쌓는 리스크, ② 컨텍스트 창의 Dumb Zone(~120k 토큰) 도달
    - 실패 모드 ②: 한 번에 너무 큰 스코프를 그릴링하려는 것
    - **해결책**: 큰 스코프를 에이전트에게 미리 작은 단위로 분해하도록 요청 → 각각 개별 세션에서 그릴링
    - 120k 토큰 = 대부분 최신 모델에서 Dumb Zone 시작점 (집중력 저하·판단력 감소)



*   **[00:08:00] ~ 렌즈 3 — 수동/능동 참여의 균형**

    - 실패 모드 ③: 너무 수동적 — LLM이 질문을 540개 쏟아내거나 스코프를 폭발시키도록 방치
    - 실패 모드 ④: 너무 능동적(고집스러움) — 저피델리티 질문에서 벗어나지 못하고 실제 코드 구현으로 넘어가지 않음
    - 그릴링은 인터뷰가 아닌 **대화** — 방향과 스코프를 주도하는 것은 사용자의 책임



*   **[00:10:00] ~ 실수 5·6 — 컨텍스트의 가치와 PRD 실수**

    - 그릴링 세션에서 쌓인 Q&A와 설계 결정들은 수만 토큰에 달하는 귀중한 자산
    - 컨텍스트 여유가 있으면 바로 구현 진행 가능; 없으면 `/write-PRD` 스킬로 핸드오프 문서 생성
    - 실패 모드 ⑤: 그릴링 세션의 컨텍스트를 버리는 것 — "이 100k 토큰을 왜 버립니까?"
    - 실패 모드 ⑥: 새 빈 컨텍스트에서 `/write-PRD`를 실행하는 것 — 그릴링 세션 안에서 바로 실행해야 그 결정들이 반영됨



*   **[00:13:00] ~ 실수 7 — 너무 약한 모델 사용**

    - 모델의 지식 두 가지: **컨텍스트 지식**(파일·프롬프트로 전달된 것) vs **파라메트릭 지식**(학습된 이해)
    - 그릴링은 파라메트릭 지식에 크게 의존 — 모델이 "아직 고려하지 않은 것"을 제안하려면 방대한 파라미터가 필요
    - 실패 모드 ⑦: 그릴링에 소형 모델 사용 → 대형 프론티어 모델 필수
    - 구현 단계에서는 컨텍스트 지식이 주를 이루므로 소형 모델도 충분히 가능



*   **[00:15:00] ~ 실수 8·9 — 병렬 그릴링과 종합 정리**

    - 실패 모드 ⑧: 한 번에 하나의 그릴링 세션만 진행하는 것
    - **병렬 그릴링 전략**: 두 세션을 동시에 열어 한 세션이 응답 생성 중일 때 다른 세션에 답변 → 처리량 2배
    - 보통 최대 2개 세션, 리서치 같은 장시간 작업이 있을 경우 3개까지 가능
    - 그릴링 실력은 연습을 통해 향상되며, 숙련될수록 병렬 수를 늘릴 수 있음
    - 9가지 요약: ① 고피델리티 질문을 억지 그릴링, ② 스코프 과대, ③ 너무 수동적, ④ 너무 능동적, ⑤ 컨텍스트 버림, ⑥ 새 컨텍스트에서 PRD 생성, ⑦ 약한 모델 사용, ⑧ 단일 세션만 운영, ⑨ 그릴링 세션 중 구현으로 너무 늦게 전환
